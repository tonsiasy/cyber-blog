# ADR 001: 采用轻量级 .env 与环境变量进行配置管理

## 状态 (Status)
已采纳 (Accepted) - 2026-10-13

## 上下文 (Context)
在 Go Web 后端开发中，配置管理通常有两种常见范式：
1. **重型方案（如 spf13/viper）**：功能丰富，支持多格式配置文件（YAML/JSON/TOML）、命令行参数绑定（pflag）、远程配置中心（Consul/Etcd）以及文件变更热重载（Live Reload）。但连带依赖复杂（如 fsnotify, mapstructure 等数十个间接依赖），启动与编译体积相对较重，且容易产生弱类型字符串取值的静默错误。
2. **轻量云原生方案（如 joho/godotenv + 系统环境变量）**：遵循云原生与 12-Factor App 原则（通过环境注入配置）。仅负责在本地开发时将 `.env` 加载到进程环境变量中，通过强类型结构体集中读取与校验。

## 决策 (Decision)
我们决定在 `cyber-blog` 项目中**采用 `godotenv` + 强类型 `Config` 结构体**作为配置管理方案，不引入 `viper`。

具体落地规范：
- 本地开发：通过 `godotenv.Load()` 读取项目根目录下的 `.env` 文件。
- 生产部署（Docker / 云服务器）：直接通过 Docker Compose 的 `environment` 或主机环境变量注入，不依赖物理配置文件。
- 核心代码：封装 `config.LoadConfig() *Config`，将环境变量映射至具有明确默认值的强类型结构体中，提供编译期和初始化阶段的类型安全。

## 结果与权衡 (Consequences)

### 正向影响 (Positive)
- **依赖纯粹度高**：避免了 Viper 庞大的依赖树，降低维护成本与安全漏洞面。
- **云原生兼容性佳**：天然与 Docker、K8s、CI/CD 流水线环境注入契合。
- **认知负荷低**：单一入口与清晰的数据流向，易于课程作业答辩与代码 Review。

### 潜在限制 (Negative / Risks)
- 不直接支持复杂的嵌套结构配置（需通过分片环境变量命名规范，如 `DB_HOST`, `DB_PORT` 等对齐）。
- 不支持运行中无需重启进程的动态配置热重载（对于博客系统，配置变更通常需要重启服务以重连连接池，热重载并非刚需）。
